# Strategy 3.2.4 — the crop the model actually gets (live `pad` calibration)

**A calibration strategy: no retrain, no FSM change, no pipeline change.** Same
checkpoint, same `not_fist`/`fist` framing (AD-21), same cursor mapper, same
runtime as 3.2.3. One number moves — the **`pad` the live detector grows its box
by** — and it is the largest single term in why live fists don't click.

It exists because of a live report: *"the non-fist reads >90% every time but the
fist caps around 55%."* At 55% a fist is **below both FSM gates** (3.2's 0.70 and
3.2.1's 0.80), so it never fires a click no matter how long it's held.

The starting hypothesis was overfitting. **It isn't** — and the measurements
below say so specifically enough to rule it out. What is actually happening is a
train/serve **crop-geometry** mismatch that has been asserted-but-unmeasured in
this repo since Strategy 2, and it lands almost entirely on the `fist` class.

Every number here is reproducible with
[`scripts/eval_crop_geometry.py`](../../../../scripts/eval_crop_geometry.py):

```bash
python scripts/eval_crop_geometry.py --stage geometry     # fast, no model
python scripts/eval_crop_geometry.py --stage classifier --limit 60
```

## The contract that was never checked

Architecture §A.3 has required this from the start:

> the live MediaPipe bbox must approximate the HaGRID training bbox (**same
> relative tightness** and `bbox_pad`), or the classifier is fed a distribution
> it never trained on.

Both halves call the *same* `padded_bbox_pixels()` with the *same* `pad = 0.15`,
so the geometry looked matched. It isn't, because the two `pad`s are applied to
**different boxes**:

| | training | live |
|---|---|---|
| box source | HaGRID's **annotated hand bbox** | MediaPipe's **21-landmark hull** |
| then grown by | `pad = 0.15` | `pad = 0.15` |

A landmark hull is not a hand bbox. HaGRID's annotation JSONs happen to carry
**both** — the bbox *and* the 21 landmarks — so the hull the live detector would
build is recoverable for every image already on disk, and the gap is measurable
without a webcam. Over the **full downloaded population** (27k–29k images per
gesture), linear scale of hull ÷ annotated box:

| gesture | hull / bbox (linear) | live `pad` that would equalize |
|---|---|---|
| **`fist`** | **0.705** | **0.42** |
| `mute` | 0.732 | 0.39 |
| `two_up` | 0.741 | 0.38 |
| `one` | 0.743 | 0.38 |
| `dislike` | 0.782 | 0.33 |
| `ok` | 0.812 | 0.30 |
| `like` | 0.821 | 0.29 |
| `palm` | 0.849 | 0.27 |
| **overall median** | **0.768** | **0.35** |

**The live crop is a ~1.3× zoom-in on what training saw, and `fist` is the worst
case in the entire label set.** The reason is anatomical, not a bug: a closed
fist's landmarks sit *inside* its own silhouette (the fingers are curled behind
the knuckles), while an open palm's reach the fingertips and nearly recover the
hand's true extent. So the class whose crop is most distorted at inference is
exactly the one class that has to be crisp for a click to fire.

### MediaPipe is not the problem

The obvious suspect — MediaPipe mis-locating hands in HaGRID stills — was
checked and cleared. Comparing MediaPipe's detected hull against HaGRID's **own
ground-truth landmark hull** on the same images gives a linear ratio of
**0.995–1.054** across all seven gestures tested (`fist` 1.028). The detector
reproduces the annotation's landmarks almost exactly.

**The entire gap is a definition mismatch between a landmark hull and a hand
bounding box**, not detection error. That matters for the fix: growing the pad
is correcting a systematic, measured offset, not papering over a flaky detector.

## What it costs at the click gate

Same held-out test images, same checkpoint, fed twice — once cropped the way it
was trained and scored (annotated bbox + 0.15), once the way the live loop feeds
it (real MediaPipe hull, pad swept). `n = 54` fists / 140 non-fists, conf-gate
0.70:

| live crop | fist click-rate | median p(fist) | **p10 p(fist)** | false-click |
|---|---|---|---|---|
| **`pad 0.15` (deployed)** | **81.5 %** | 0.927 | **0.464** | 0.7 % |
| `pad 0.25` | 90.7 % | 0.984 | 0.784 | 0.7 % |
| **`pad 0.35`** | **94.4 %** | 0.984 | **0.932** | **0.0 %** |
| `pad 0.45` | 94.4 % | 0.985 | 0.948 | 0.0 % |
| *annotated bbox (what the 100% test score used)* | *100 %* | *0.985* | *0.971* | *0.0 %* |

The column that explains the live complaint is **p10** — the 10th-percentile
confidence on a *real* fist, i.e. the marginal squeeze. At the deployed pad it is
**0.464**: one fist in ten reads at or below ~46%, which is the "caps around 55%"
report almost exactly. Correcting the pad moves that to **0.932**, and it costs
nothing — false clicks go *down*, 0.7% → 0.0%.

Note that the median barely moves (0.927 → 0.984). **A good average was hiding a
bad tail**, and the tail is what a click depends on: the FSM needs `K`
consecutive frames over the gate, so the frames that fall in that bottom decile
are precisely the ones that break a confirm streak.

## Why "overfit" is the wrong diagnosis

The instinct was right that something is badly wrong at serving time; the
mechanism isn't overfitting, and the evidence is specific:

1. **No variance gap to overfit into.** Val 1.0000 and test 1.0000 on a
   user-grouped split that was independently leakage-audited (3.2.2). Train and
   held-out agree perfectly — the classic overfitting signature (train ≫ held-out)
   is absent.
2. **The degradation is geometric, and it reverses.** Feed the *same* model the
   *same* images with the crop corrected and the fist click-rate goes
   81.5% → 94.4%. Overfitting does not undo itself when you change the framing.
3. **The tuned checkpoint is the most robust of the five, not the least.** Under
   live geometry at the deployed `pad 0.15`:

   | checkpoint | fist click-rate | false-click |
   |---|---|---|
   | **`week4_tuned_fistvsrest`** (3.2.2 champion) | **81.5 %** | **0.7 %** |
   | `struct_unfreeze2_auglive` (tied on val, passed over) | 85.2 % | 3.6 % |
   | `struct_unfreeze2` (no aug) | 66.7 % | 2.9 % |
   | `struct_aug_only` (frozen probe) | 66.7 % | 2.9 % |
   | `fistvsrest_frozen` (the 3.2 model it replaced) | 77.8 % | **10.7 %** |

   The champion beats the model it replaced on both axes, and its false-click
   rate is **15× better**. Unfreezing two blocks did not make it brittle — the
   frozen probe collapses harder under the same shift.

4. **The confidence *feels* worse partly because it's better calibrated.** The
   old 3.2 checkpoint reads a median p(fist) of **0.998** — but its p10 is
   **0.017**, i.e. it is bimodal and dead-certain in both directions, including
   when it's wrong (hence 10.7% false clicks). The champion trained with **label
   smoothing 0.062**, which caps its achievable confidence near **0.969** by
   construction, and its head-weight norm is 0.60 against the old probe's 14.5.
   A number that reads lower on the HUD is not automatically a worse decision —
   but at `pad 0.15` the fist genuinely does fall under the gate too often, and
   that part is real.

**Two things were also ruled out** on the way: the ONNX backend 3.2.3 introduced
(max probability disagreement vs. torch on real crops: **2.3e-07**, not the
random-noise parity check but real hand crops), and any class bias in the head
(per-class weight norms 0.598 / 0.602, biases −0.005 / −0.020).

## What this does *not* fix

`pad 0.35` recovers most of the gap but not all of it — **94.4% against the
annotated crop's 100%**. The residual is the part a single scalar can't reach:
the equalizing pad is **0.42 for `fist` and 0.27 for `palm`**, and the live loop
doesn't know which one it's looking at before it classifies. One pad is
necessarily a compromise across a spread the geometry table quantifies.

Everything outside crop geometry is also untouched and still unmeasured:
webcam sensor and lighting, and the **arm's-length pose regime HaGRID simply does
not contain**. This measurement is on HaGRID stills, so it is a **lower bound**
on the live gap — it isolates geometry, and the live 55% is geometry *plus*
whatever domain shift the webcam adds on top.

## The change

**Accepted, 2026-07-28 (Ted's call).** The live `--pad` default moves
**0.15 → 0.35** in `play.py`, `webcam_demo.py`, and the dashboard tracker
(`src/eval_dashboard/tracker.py`). Training's `bbox_pad` in
`configs/data_fistvsrest.yaml` is untouched — it pads the *annotated* box, which
is a different contract from the live hull. Per CLAUDE.md the crop tightness is a
preprocessing call for the human, and 2.1's fix-2 already carried the caveat that
matters here:

> changing live pad *without* retraining trades one mismatch for another. The
> principled version is to pick the pad that reads best, then **retrain at that
> pad**.

That caveat is why the retrain-on-landmark-hull path (below) stays open rather
than superseded — 0.35 is the recalibration, not the principled fix. It is
**instantly revertible**: `--pad 0.15` on any of the three entry points restores
the old behavior. The recommendation is still **untested against the real
game** — this measurement is on HaGRID stills (a lower bound, see above) — so
the live A/B is the next checkpoint on this change, same as every strategy since
3.1:

```bash
# now the default; --pad 0.15 restores the pre-3.2.4 behavior for comparison
python -m src.control.play --checkpoint models/week4_tuned_fistvsrest/best.pt \
    --strategy 3.2.1

# watch the confidence respond to pad in real time ( [ tightens, ] loosens )
python -m src.rt.webcam_demo --checkpoint models/week4_tuned_fistvsrest/best.pt
```

## Decisions this surfaces, left open (Ted's calls)

- ~~Whether `--pad` default moves 0.15 → ~0.35~~ **Accepted 2026-07-28** — done
  in `play.py`, `webcam_demo.py`, and the dashboard tracker. The offline evidence
  was one-directional (better fists *and* fewer false clicks); 0.35 vs 0.45 was
  indistinguishable in this data, and 0.35 was picked as the more conservative
  of the two. **The live A/B against the actual game is still open** — per
  project convention since 3.1 the live feel is the real verdict, not this
  offline table.
- **Whether to retrain on landmark-hull crops instead** — the principled fix,
  still open.
  HaGRID's landmarks are already on disk, so training could build its crop the
  *same way the live detector does*, making the live box a **1.00×** match by
  construction and removing the per-gesture spread that a single pad can't. Costs
  a data-layer option (`crop_source: bbox | landmark_hull`) and one ~2.5 h
  training run; it would also make every published accuracy number a
  different-crop number, so it's a comparability decision, not just a retrain.
- **Whether `struct_unfreeze2_auglive` deserves a live A/B.** It tied the champion
  on val (1.0000) and was passed over by an arbitrary tie-break, and it is the
  *best* of the five at the deployed `pad 0.15` (85.2% vs 81.5%) — but worse on
  false clicks (3.6% vs 0.7%), and at the corrected pad the champion matches it.
  A real trade, not a free win.
- **Whether the open-set `ok` metric should be re-run under live geometry.** Every
  false-click number this project has published, including 3.2's headline
  0.8%, was measured on annotated crops. The `ok` row moved 6.8% → 0.8% on
  *annotated* boxes; nobody has checked what it does on hulls.

## What did NOT change

The checkpoint, the `not_fist`/`fist` framing (AD-21), the crop *contract* and
`padded_bbox_pixels` itself, training's `bbox_pad` (still 0.15 on the annotated
box), the cursor mapper and adaptive box (3.1/3.1.1), the EMA/dead-zone, the
FSM's logic and both presets' values (3.2, 3.2.1), the 3.2.3 runtime (ONNX
backend, threaded capture, 60 ms click hold), and the kill-switch. 3.2.4 is a
measurement plus one accepted flag default (live `pad` only).

## Verdict

*Measured, and the recommendation adopted; the live A/B is what's untested.* The
train/serve crop gap was real, quantified, and asymmetric against the one class
that fires clicks: the live crop was **1.3× tighter** than training's, worst on
`fist` (0.705), and at the old deployed `pad 0.15` that put a real fist's
10th-percentile confidence at **0.464** — under both FSM gates. The new default,
`pad 0.35`, takes it to **0.932** and fist click-rate 81.5% → 94.4% with false
clicks 0.7% → 0.0%, on HaGRID stills. **Whether that translates at arm's length
in front of the actual game is the open question, same as every strategy since
3.1.**
