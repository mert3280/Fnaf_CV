# Strategy 3.2.2 — tuned champion checkpoint (AD-22/23/24, Week 4)

**A retrain of [Strategy 3.2](03.2-fist-vs-rest.md), not a reframe.** Same task,
same label space (`not_fist` = no-click, `fist` = click), same cursor + click
pipeline, same crop contract. What changes is the **checkpoint** feeding stage 2,
and — new this round — *how it gets there and how it's served*:

| | 3.2 | **3.2.2** |
|---|---|---|
| Head init | timm default (`r=1/sqrt(out_features)`) | **`pytorch_linear`** (AD-22) |
| Backbone | frozen | top **2 blocks unfrozen** (AD-08 Stage B) |
| Selection | single run | 60-trial Optuna TPE (Arm A) + 5-cell structural grid (Arm B), **val only** |
| Val / test acc | 0.9221 / 0.9358 | **1.0000 / 1.0000** (327/327) |
| Provenance | checkpoint path on a command line | **MLflow Model Registry**, `fnaf-click-classifier` v1 @`champion` (AD-24) |
| Reproduce | `python -m src.train` | `python -m src.pipeline.run --dag training` (AD-23) |

The click FSM is untouched by this strategy — 3.2.2 is orthogonal to
[3.2.1's FSM presets](03.2.1-snappier-fsm.md): point `--strategy 3.2` or
`3.2.1` at whichever checkpoint you're testing, this one included.

## What actually moved the number

Attributed, not just reported (the point of the exercise — see the honest-caveats
framing below):

| step | val | Δ |
|---|---|---|
| deployed baseline (`fistvsrest_frozen`, 3.2) | 0.9221 | — |
| **head init fixed only** (AD-22) | 0.9740 | **+5.19** |
| + 60-trial TPE search (3-seed mean, top 3) | 0.9827 | +0.87 |
| + unfreeze 2 backbone blocks (AD-08 Stage B) | 0.9968 | +1.41 |
| + augmentation | 1.0000 | +0.32 (within noise) |

The dominant term is **not** hyperparameter search — it's a bug. timm's
EfficientNet-family head init sizes its `Linear` init range by *class count*, so
a 2-class head starts ~25× wider than PyTorch's own default: ±27 logits, CE 2.70
instead of ln(2)=0.69. The 3.2 checkpoint's "val still climbing at ep40" note was
that init being slowly undone, not an epoch-budget problem. Full derivation:
[AD-22](../../architecture-and-decisions.md#ad-22--head-initialization-for-a-2-class-head--proposed-2026-07-26--teds-call).

**Read the perfect score correctly — it means the benchmark is saturated, not
that the model is flawless.** 327/327 survived an independent eval path and a
leakage audit (`scripts/audit_split_leakage.py`: 0 duplicate files across splits;
test→train nearest-neighbour cosine max 0.845 vs. a train→train control of
0.891), so it isn't leakage. But it also means offline accuracy has run out of
room to tell 3.2.2 apart from weaker candidates, and on the one metric that still
had headroom — false clicks on the **unseen** `ok` gesture — tuning changed
**nothing**: 0.8% before, 0.8% after. The open-set generalization question 3.2
exists to answer is not what improved here.

## New this round: orchestration + deployment (not a pipeline change)

Two infrastructure decisions rode along with the retrain — neither touches the
webcam→cursor→click pipeline itself, both change how the checkpoint is produced
and handed to the runtime:

- **AD-23 — a local DAG, not a scheduler.** `src/pipeline/` orders and caches
  the training tasks (topological order, freshness, retries, JSON run records),
  triggered by `--if-data-changed`, not cron — there's nothing here that arrives
  on a clock.
- **AD-24 — MLflow Registry + a self-describing pyfunc artifact.** The champion
  alias is one queryable answer to "which model is live," and the pyfunc carries
  its own preprocessing so a served model can't drift from the crop/normalize
  contract (architecture §A.3). `src/serve/app.py` exposes it over Flask
  (`/health`, `/model`, `/predict`) for validation and batch scoring — **the
  live game loop still calls the model in-process** (endpoint p50 40.8 ms vs. a
  ~33 ms frame budget), so this doesn't change runtime latency.

## Decisions this strategy surfaces, left open

- **Whether `pytorch_linear` becomes the project-wide head-init default** (would
  make the pre-3.2.2 accuracy numbers "old-init" figures, not directly
  comparable) — AD-22 is explicitly **Proposed**, Ted's call.
- **Whether `week4_tuned_fistvsrest` replaces `fistvsrest_frozen_mnv3_large` as
  the checkpoint `play.py`/the dashboard default to** — an offline-saturated
  benchmark can't make this call by itself; per project convention the live
  arm's-length test is the verdict, same as every strategy since 3.1.

## What did NOT change

The cursor mapper (3.1.1 adaptive box), MediaPipe detector, EMA/dead-zone
smoothing, click FSM logic and its 3.2/3.2.1 presets, the crop contract, the
kill-switch, and the task framing itself (`not_fist`/`fist`, AD-21). A 3.2.2
checkpoint is a drop-in for a 3.2 one.

## How to run

```bash
# live demo / play, straight from the checkpoint (either FSM preset applies)
python -m src.rt.webcam_demo --checkpoint models/week4_tuned_fistvsrest/best.pt
python -m src.control.play    --checkpoint models/week4_tuned_fistvsrest/best.pt --strategy 3.2.1 --dry-run

# or the registry-served path (validation / batch scoring, not the live loop)
python -m src.serve.app
curl -s http://127.0.0.1:8765/health

# reproduce the model itself (~2.5 h CPU)
python -m src.pipeline.run --dag training
```

## Verdict

*Pending live A/B against 3.2* — same convention as every strategy since 3.1:
the offline number is in (and saturated), the open-set `ok` metric didn't move,
and the number that decides adoption is how it feels driving the real game at
arm's length.
