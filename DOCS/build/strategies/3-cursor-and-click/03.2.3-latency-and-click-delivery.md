# Strategy 3.2.3 — latency budget + click delivery

**A runtime-engineering strategy, not a model or a tuning one.** Same checkpoint,
same `not_fist`/`fist` framing, same cursor mapper, same crop contract, same FSM
*logic*. What changes is **how fast the loop runs** and **what a "click" actually
sends to Windows**.

It exists because the two complaints from the live tests — *"FPS is really bad
and slow"* and *"some clicks don't get registered"* — are **not two problems**.
They're one problem with two symptoms plus one independent bug:

- The frame loop ran at **21 FPS** (on AC — on battery, ~9) with **67 ms** of
  stale-frame lag on top, and
  every FSM knob is denominated in **frames** (`K`, `grace`) — so a slow loop
  makes clicks slow *and* drops the fast ones.
- Separately, the click we send has **zero hold time** (button-down and
  button-up in a single `SendInput` batch), which a game that samples input once
  per game frame can miss entirely.

Both are fixed in code; the whole thing is revertible with three flags
(`--backend torch --no-threaded-capture --click-hold 0`).

Every number below is measured on this machine with
[`scripts/bench_pipeline.py`](../../../../scripts/bench_pipeline.py), which times
the **real** loop stages against the real camera:

```bash
python scripts/bench_pipeline.py --seconds 8 --preview --stale
```

## Where the frame time actually goes

Measured 2026-07-27, this box **on AC power** (see the power-state note below —
it matters more than any fix here), `week4_tuned_fistvsrest` (mnv3_large,
224 px), CPU, 640×480 DSHOW camera, HUD on. Per-frame **medians** over 8 s per
config:

| backend | capture | read | detect | prep | model | hud | **total** | **FPS** |
|---|---|---|---|---|---|---|---|---|
| torch | sync | 0.2 | 19.1 | 2.7 | 20.7 | 2.7 | **45.7** | **21.0** |
| torch | threaded | 0.0 | 19.2 | 2.8 | 20.6 | 2.6 | 45.8 | 21.3 |
| onnx | sync | 0.2 | 20.4 | 3.1 | 6.2 | 2.6 | 33.5 | 27.9 |
| **onnx** | **threaded** | 0.0 | 19.2 | 2.6 | **6.3** | 2.7 | **32.6** | **28.3** |

**≈ 21 FPS → ≈ 28 FPS**, and at 28 FPS the **camera's 30 Hz is the ceiling** —
further compute optimization buys nothing. Three findings behind that table, two
of which overturned what this page predicted before the benchmark existed:

1. **The classifier was the bottleneck, and the ONNX artifact we already export
   is 3.3× faster on the same CPU** — 20.7 ms → 6.2 ms *in the live loop* (6.5 ms
   vs. 23.9 ms in isolation). `model.onnx` sits next to every checkpoint, already
   exported and parity-checked by the training DAG (AD-11); it simply wasn't what
   the loop loaded.
2. **Threaded capture is a *latency* fix, not a throughput one.** The predicted
   saving was −33 ms/frame from not blocking on `cap.read()`. Wrong: when the loop is slower
   than the camera, the synchronous `read()` returns in **0.2 ms** — because it's
   serving from the driver's backlog, i.e. handing back a **stale** frame. Measured
   backlog depth (run a slow loop, then count the frames that come back instantly):
   **2 frames ≈ 67 ms of input lag**, bounded but permanent. So threading changes
   the FPS column by ~nothing and removes ~67 ms of "the hand I'm classifying is
   where the hand *was*" — which is exactly the term that eats clicks.
3. **`torch.set_num_threads(4)` is not the −6 ms micro-optimization it was
   filed as — it's worth a third of the frame rate.** With torch's library default (16 threads on
   this CPU) the same loop measures **14.7 FPS** instead of 21.0, and the
   *preprocessing* stage — torchvision ops on a single 224 px tensor — blows up
   from 2.6 ms to **138–161 ms** in some runs. A 16-thread pool fighting
   MediaPipe's own XNNPACK threads for 16 logical cores loses badly, and because
   preprocessing is torchvision, this hurts the **ONNX path too**. The cap is
   applied for both backends.

### Power state costs more than everything on this page combined

Halfway through this work every measurement got ~2.1× slower at once — every
stage, uniformly, with the CPU otherwise idle (9% load, no competing process).
What *was* verified at that point: this is a **laptop** (Core Ultra 7 165H), it
was **discharging**, and the CPU was sitting at its 1.4 GHz base clock. The
power state is the explanation that fits a uniform, load-independent 2.1× on
every stage — though the earlier runs' power state wasn't recorded at the time,
so treat the AC/battery labels below as the likely reading rather than a
controlled A/B. Same code, same machine, same day, model forward in isolation:

| | classifier (torch) | classifier (ONNX) | whole loop |
|---|---|---|---|
| boosting (on AC) | 23.9 ms | **5.3 ms** | **28.3 FPS** |
| base clock (on battery) | 51.6 ms | 11.2 ms | **9–11 FPS** |

**Plug the laptop in before playing, and re-check with
`scripts/bench_pipeline.py`, which now stamps the power state onto its report.**
On battery the loop runs at 9–11 FPS *with
every fix in this strategy applied* — worse than the 21 FPS the unfixed loop
managed on AC. If clicks feel unresponsive, check the power state before
suspecting anything in this repo; it is the single largest term in the budget,
and it's plausible it was a large part of the original "FPS is really bad"
complaint.

**So read the table above as a comparison, not a spec.** Absolute FPS depends on
power state, and on what else is running (Spotify, Discord, Chrome, VS Code and
the eval-dashboard server were all up; the dashboard competes with `play.py` for
the same cores). What is stable across all five benchmark runs is the **ordering
and the size of the gap**: the ONNX classifier stage measured 5.3–13.5 ms against
torch's 20.7–51.6 ms, never once slower, on AC and on battery alike.

Also worth recording: **`torch` here is a CPU-only build** (`2.10.0+cpu`,
`cuda.is_available() == False`) despite AD-02b's RTX 4060, so `play.py --device
cuda` is currently a flag that cannot work. It stays that way — ONNX-on-CPU
already reaches the camera ceiling, so a CUDA wheel would buy the live loop
nothing (it's a *training*-time argument).

## The fixes, and what each actually bought

| # | change | measured effect | risk |
|---|---|---|---|
| 1 | **ONNX Runtime for stage 2**, parity-checked at load ([`backends.py`](../../../../src/rt/backends.py)) | model 20.7 → **6.2 ms**; 21 → 28 FPS | low — falls back to torch if parity fails |
| 2 | **Cap torch threads at 4** (both backends — preprocessing is torchvision) | 14.7 → **21.0 FPS** on the torch path; prevents the preprocessing blow-up | none |
| 3 | **Threaded capture**, newest-frame-only ([`capture.py`](../../../../src/rt/capture.py)) | **−67 ms input lag**; FPS unchanged | low — pure decoupling |
| 4 | Skip `move_to` when the mapped pixel didn't change | one fewer `SendInput` per frame | one behaviour change: with the hand dead-zone-still, a bump of the *physical* mouse is no longer overridden until the hand moves again |
| 5 | `--hud-every N` to render the preview every Nth frame | −2.7 ms/frame when used | cosmetic |

MediaPipe's ~19 ms is now the largest term. The honest next lever is a smaller
detection input (downscale **for detection only**, full-res crop for the
classifier) — left undone, because at 28 FPS against a 30 FPS camera it would buy
nothing and it trades against detection range at arm's length.

## Why low FPS eats clicks (and what fixes it)

This is the part the FSM presets can't fix, because `K` and `grace` count
**frames**, and a frame was worth 46 ms instead of 33 ms — on top of ~67 ms of
stale-frame lag:

| gate | at 21 FPS (before) | at 28 FPS (after) |
|---|---|---|
| `K = 2` confident fist frames (3.2.1) | **95 ms** of held fist | 71 ms |
| `K = 3` (3.2) | **143 ms** | 107 ms |
| re-arm (`K` confident `not_fist` frames) | 95–143 ms *after* the click | 71–107 ms |
| re-arm + `cooldown 0.30 s` before the next click can fire | **~0.44 s** | ~0.39 s |
| `grace = 10` ambiguous frames before disarm | **0.48 s** | 0.36 s |
| **+ camera backlog (synchronous read)** | **+67 ms on every one of these** | **0** |

A quick squeeze-and-release — the natural way to click a door button — has to
survive both columns: the fist must be held long enough to produce `K` confident
frames **and** it is being classified from a frame that is ~67 ms old. A ~150 ms
squeeze that reads fine to the user has, in the old loop, roughly one frame of
margin. No confidence threshold or `K` value recovers a pose the loop never
sampled.

**The fix is the frame rate, not the knobs.** 3.2.3 deliberately changes **no FSM
default** — after the loop is fast, `K`/conf/grace/cooldown mean what 3.2/3.2.1
intended them to mean, and Ted's live A/B between those presets becomes a fair
test for the first time (right now both presets are being judged through a 90 ms
sampling interval). Whether `grace` and `cooldown` should be re-expressed in
**milliseconds instead of frames** so they stop drifting with FPS is a real design
question this surfaces — see the open decisions below.

## The independent bug: our click has no hold time

`InputSim.click()` calls `pydirectinput.click()`, which issues **one**
`SendInput` with `dwFlags = MOUSEEVENTF_LEFTDOWN | MOUSEEVENTF_LEFTUP` — press
and release in the *same input event*, hold time **0 ms** (verified by reading
`pydirectinput`'s source, not by assumption).

FNAF 1 is a Clickteam Fusion / DirectX title that samples mouse state once per
game frame (~16 ms at 60 FPS). A press-and-release that begins and ends between
two samples can be observed as *"button was up, and is still up"* — the click
never happened as far as the game is concerned. This is consistent with the
symptom: clicks that vanish **non-deterministically**, with the HUD showing the
FSM fired and `sim.clicks` incrementing. It is independent of FPS, and it is
independent of the model — no amount of retraining or FSM tuning touches it.

The delivery change (three parts, all in
[`input_sim.py`](../../../../src/control/input_sim.py)):

- **Hold the button ~60 ms**: `mouseDown()` → hold → `mouseUp()`, so 3–4 game
  frames observe the pressed state. `--click-hold 0.06`, tunable — this is a
  live-feel number, so the value is Ted's call (CLAUDE.md); `--click-hold 0`
  restores the old pulse for a clean A/B.
- **Without blocking the frame loop.** `click()` presses and arms a deadline;
  `sim.tick()` at the top of each frame sends the release. A blocking 60 ms
  `sleep()` would have cost most of the frame rate the rest of this strategy just
  bought — at 28 FPS the hold spans ~2 frames instead.
- **Freeze the cursor while the button is down** (`is_pressed` suppresses
  `move_to`), so press and release land on the *same* pixel. A cursor that drifts
  mid-press is a drag, and on a target the size of a FNAF door button the game
  reads that as a miss.

The kill-switch contract is preserved and extended: `kill()` releases the button
*before* disabling output, so killing mid-press can never leave the physical
mouse button stuck down. Verified by unit test, along with the hold sequence, the
cursor-freeze, and the `--click-hold 0` fallback.

## What does NOT change

The checkpoint (any 3.2/3.2.2 one), the `not_fist`/`fist` framing (AD-21), the
crop contract (A.3) — both backends consume the *same* `Preprocessor` tensor, and
ONNX is gated on a load-time parity check (`max|torch−onnx|` on probabilities,
measured **1.2e-07**, tolerance 1e-3) precisely so this stays true — the cursor
mapper and its adaptive box (3.1.1), the EMA / dead-zone, the FSM's **logic** and
both presets' **values** (3.2, 3.2.1), and the ESC kill-switch. A 3.2.3 run is a
3.2.x run that samples faster and presses longer.

Only `play.py` is on the new path. `webcam_demo.py`, `compare_demo.py`, and the
eval dashboard's tracker still use the old capture and the torch backend — worth
knowing when comparing FPS between them, and the obvious next port.

## Decisions this strategy surfaces, left open (Ted's calls)

- **`--click-hold` duration.** 60 ms comes from the 60 Hz game-frame argument, not
  from a measurement of FNAF itself. If clicks still drop, raise it before
  touching anything else; the live test is the verdict.
- **Frame-count vs. time-based FSM gates.** Should `K`/`grace`/`cooldown` be
  re-expressed in ms so click feel stops moving with the frame rate? Deliberately
  *not* done here — it would make 3.2 and 3.2.1's published values need a
  translation, so it's a compatibility decision, not a refactor.
- **Whether the FSM presets want re-tuning now.** A 33 % faster loop makes `K`
  frames worth less wall-clock time, so 3.2 and 3.2.1 both got slightly snappier
  for free. That may be enough, or it may make room for a stricter gate. Per
  CLAUDE.md this is a live-feel call, and no preset value was touched.
- **Detection downscale.** Running MediaPipe on a half-res frame is the next
  ~−10 ms, paid for in detection range at arm's length — the exact regime 3.1.1
  fought for. Not worth it at the camera ceiling; revisit only with a faster camera.

## How to test it

```bash
# the new defaults (onnx + threaded capture + 60 ms hold)
python -m src.control.play --checkpoint models/week4_tuned_fistvsrest/best.pt --strategy 3.2.1 --dry-run

# full revert to pre-3.2.3 behaviour, for the A/B
python -m src.control.play --checkpoint models/week4_tuned_fistvsrest/best.pt --strategy 3.2.1 \
    --backend torch --no-threaded-capture --click-hold 0

# live, on a door button (the symptom that started this)
python -m src.control.play --checkpoint models/week4_tuned_fistvsrest/best.pt --strategy 3.2.1

# re-measure the budget after any loop change
python scripts/bench_pipeline.py --seconds 8 --preview --stale
```

The HUD footer now reads `28.3FPS onnx drop0` — `drop` is the count of frames the
camera produced that the loop was too slow to take, i.e. a live readout of how
far behind the camera the pipeline is running.

Three failure modes that used to look identical are now distinguishable:

| symptom | reading | cause |
|---|---|---|
| FSM fired (`clicks` went up), game did nothing | HUD shows the click | **delivery** — raise `--click-hold` |
| fist held, FSM never confirmed | streak line stalls below `K` | **sampling** (FPS/`drop`) or **confidence** (model) |
| click landed somewhere else | cursor moved during the press | shouldn't happen now — cursor is frozen while pressed |

## Verdict

*Implemented; live test pending.* Measured, reproducible: **21.0 → 28.3 FPS**
(HUD on, camera-capped at 30) and **−67 ms** of input lag, with the click now
held ~60 ms instead of 0. Unlike 3.2.1 / 3.2.2 there's no accuracy number here by
construction — and per the project's convention since 3.1, whether the clicks
*land* is decided by driving the real game at arm's length, not by this table.

**What is not verified:** that the hold time fixes the missed clicks in FNAF
itself. The 0 ms-pulse diagnosis is solid on the input-simulation side (read
straight out of `pydirectinput`'s source) and the fix is verified to emit
down/hold/up, but nothing here has yet been tested against the running game — no
part of this project has, Step 5 is still open. If clicks still drop at
`--click-hold 0.06`, the next suspects are the hold duration and FNAF's window
mode/admin elevation (see `keyboard_mock_controller.py`), not the model.
